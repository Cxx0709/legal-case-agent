# 劳动争议律师 AI 助理 MVP 设计规格

## 1. 产品目标

为中国劳动争议律师提供一个可在本地运行的 Web 工具。律师上传一组案件材料后，系统将材料整理为可继续工作的案件资料包，减少阅读、摘录、排序和制表时间。

系统只辅助整理材料，不代替律师作出法律判断。所有事实、日期、金额和风险提示均应保留材料来源；无法确认的信息必须标记为待核实，不得补造事实。

## 2. 目标用户与首版场景

首版服务于 5～50 人律所中的劳动争议律师。典型输入包括：

- 劳动合同、规章制度与解除通知；
- 仲裁申请书、答辩书和裁判文书；
- 工资流水、社保记录和考勤记录；
- 微信聊天记录及其他文本或图片证据。

首版的成功标准是：用户能够在一个案件中上传材料、触发分析，并获得一份可追溯、可人工修订的结构化报告。

## 3. MVP 范围

### 3.1 输入

支持批量上传 PDF、DOCX、TXT、PNG、JPG 和 JPEG 文件。系统校验文件类型、单文件大小和案件总容量，拒绝不支持或无法读取的文件，并向用户说明具体原因。

PDF、DOCX 和 TXT 使用本地解析器提取文字。图片在首版中仅在配置了兼容模型的视觉能力时参与识别；没有视觉能力时保留文件并标记为“需要人工查看”，不另建 OCR 服务。

### 3.2 输出

每次分析生成以下六个部分：

1. 案件摘要：案件类型、当事人、请求、关键金额、当前程序阶段。
2. 时间轴：日期、事件、涉及主体、来源和可信程度。
3. 证据目录：证据名称、证明事项、真实性/合法性/关联性提示、风险和来源。
4. 争议焦点：双方主张、已知事实、待核实事项和关联证据。
5. 材料缺失项：为核实事实或支持主张仍需补充的材料。
6. 庭审准备清单：围绕争议焦点形成的核对与准备事项。

报告页面必须展示“AI 辅助整理，不构成法律意见”的提示。用户可以在浏览器中查看结构化结果；首版不实现 Word/PDF 导出。

### 3.3 明确不做

首版不包含用户账户、组织权限、计费、在线协作、生产级对象存储、向量数据库、独立 OCR 服务、裁判文书商业数据库、自动法律结论、自动提交仲裁材料或复杂多 Agent 框架。

法律检索留作后续独立里程碑。首版可以在报告中列出“建议核验的法律问题”，但不得生成无来源的法条或案例引用。

## 4. 技术架构

采用单体 Python 应用，以最少组件完成闭环：

- FastAPI：HTTP API 与本地 Web 服务；
- 服务端渲染页面：上传、进度和报告查看；
- SQLite：案件、文件、分析任务和报告元数据；
- 本地文件目录：保存上传材料与解析文本；
- OpenAI 兼容 HTTP API：调用 DeepSeek、通义千问或其他兼容模型；
- 后台任务：使用应用内任务执行首版分析，不引入消息队列。

前后端不拆分，避免重复构建 API 客户端、鉴权和部署链路。模型访问封装为单一客户端，并通过环境变量设置基础地址、API Key 和模型名称。

## 5. 核心组件

### 5.1 案件与文件管理

负责新建案件、接收上传文件、生成安全文件名、记录原始名称和校验结果。每个案件使用独立目录，文件路径不得由用户输入直接拼接，避免目录穿越。

### 5.2 文档解析

根据文件类型调用对应解析器，统一输出：文档 ID、页码或段落位置、文本内容和解析警告。解析失败不应终止整个案件；失败文件进入报告的待处理清单。

### 5.3 分段与来源标记

解析文本按文档和位置分段。每个片段携带稳定来源标识，例如“工资流水.pdf，第 2 页”。模型输出中的事实项必须引用一个或多个来源标识。

### 5.4 分析流水线

首版采用顺序流水线，而不是自治多 Agent：

1. 从材料中抽取主体、日期、金额、主张、行为和证据线索；
2. 合并重复信息，同时保留相互矛盾的陈述；
3. 生成时间轴与证据目录；
4. 基于已抽取信息整理争议焦点、材料缺失项和准备清单；
5. 校验结构化输出、来源引用和必填字段；
6. 保存最终报告。

每个阶段使用明确的 JSON 输入输出结构。格式校验失败时最多重试一次；仍失败则记录错误，允许用户重新运行。

### 5.5 报告展示

报告页面按六个固定部分展示结果，所有事实项旁显示来源。低可信或相互矛盾的信息使用醒目标记。原始材料只在本地访问，不生成公开链接。

## 6. 数据模型

SQLite 包含四张核心表：

- `cases`：案件名称、状态、创建与更新时间；
- `documents`：案件 ID、原始文件名、存储路径、类型、解析状态和警告；
- `analysis_runs`：案件 ID、运行状态、模型、开始/结束时间和错误信息；
- `reports`：运行 ID、结构化 JSON、版本和创建时间。

报告内容首版以版本化 JSON 保存，避免为尚未稳定的分析字段创建大量表。上传文件和解析文本保存在案件目录中；数据库仅保存受控相对路径。

## 7. 主要数据流

1. 用户创建案件并批量上传文件。
2. 服务校验文件并写入案件目录，同时创建文档记录。
3. 用户触发分析，系统创建分析运行记录。
4. 解析器逐份提取文本并生成来源片段。
5. 分析流水线调用模型并校验结构化结果。
6. 系统保存报告，将运行状态更新为成功或失败。
7. 用户查看报告、来源和待人工处理项。

## 8. 错误处理与安全边界

- 上传失败：逐文件报告，已成功上传的文件保留。
- 解析失败：跳过单个文件，报告中列明原因。
- 模型超时或限流：记录可重试错误，不覆盖上一次成功报告。
- JSON 不合法：自动修复或重试一次，失败后停止该次运行。
- 来源缺失：相关结论不得进入已确认事实，改列为待核实项。
- 文件安全：限制扩展名、MIME 类型、大小和路径；不执行上传内容。
- 数据保护：默认仅监听本机地址；日志不记录正文、API Key 或完整个人敏感信息。
- 删除案件：首版不提供删除接口，避免误删；需要时由管理员在本地处理。

## 9. 配置与运行

应用通过环境变量读取：

- `LLM_API_KEY`：模型服务密钥；
- `LLM_BASE_URL`：OpenAI 兼容接口地址；
- `LLM_MODEL`：模型名称；
- `APP_DATA_DIR`：案件数据目录，默认使用项目下的本地数据目录；
- `MAX_FILE_MB`：单文件大小限制。

仓库提供 `.env.example`，但不提交真实密钥或案件材料。默认提供脱敏模拟案件，确保没有模型密钥时仍能了解输入结构并运行基础测试；完整分析需要有效的模型配置。

## 10. 测试与验收

最小自动化测试覆盖：

- 文件类型、大小与路径安全校验；
- TXT、DOCX 和文本型 PDF 的解析；
- 来源片段生成；
- 模型 JSON 输出校验与一次重试；
- 分析失败不会覆盖已有成功报告；
- 一份脱敏模拟劳动争议案件的端到端流程，模型调用使用固定响应替代。

人工验收使用模拟案件完成以下操作：创建案件、上传多类材料、触发分析、查看六部分报告、定位每项事实来源，并看到解析失败或信息冲突的提示。

## 11. 后续里程碑

MVP 验证有效后再按实际需求增加：

1. OCR 与聊天记录专项解析；
2. 报告人工编辑及 Word/PDF 导出；
3. 权限隔离、审计日志和私有化部署；
4. 具备可靠引用的法规与案例检索；
5. 异步任务队列和对象存储。

这些能力不提前进入首版代码结构，只有出现真实使用需求时再扩展。
